# Dashboard speed baseline, 8 Nov 2026

Reference numbers for the dashboard performance plan (phases 0 to 5). Taken before any fix.

- **Where:** production, https://asklarder.com.au (deployment `dpl_5Mn82JiRmAnaM8UBhmoryb3caomm`, Vercel functions in iad1 Washington, Supabase larder-dev in ap-southeast-2 Sydney).
- **From:** Melbourne, desktop Chromium 1280x800.
- **How:** `PLAYWRIGHT_BASE_URL=https://asklarder.com.au PERF_LABEL=baseline npx playwright test tests/e2e/perf.spec.ts`. Throwaway Kitchen Hand and manager accounts in coachmans-arms-wizard, created and deleted by the spec.
- **Measured:** request sent (or nav link tapped) until the page's own heading is visible. 1 cold run, then 3 warm runs; the median of the warm runs is what counts. Budget 750 ms.

## Server breakdown (local dev server in Melbourne, PERF_TIMING=1)

Run from Melbourne against Sydney, so each Supabase trip costs about 50 to 100 ms here instead of about 200 ms from iad1. Useful for the shape of the critical path, not the absolute numbers. Typical warm request:

| Scope | Total | Steps (each awaited one after another) |
|---|---|---|
| staff layout | ~830 ms | getCurrentStaff 300, outstandingAcks 200, department 100, venue 150 |
| staff home page | ~1800 ms | getCurrentStaff 200 to 380, Promise.all 470 to 950, sectionsCount 60, continuePhoto 60, activityPhoto 95, department 15, b2Overview 200, department again 15, hub 470 to 590 |
| staff modules page | ~370 ms | getCurrentStaff 220, modules 80, progress 65 |
| owner layout | ~570 ms | getCurrentStaff 300 to 400, venue 180 to 400 |
| owner dashboard page | ~1450 ms | requireOwnerPageStaff 320 to 420, Promise.all 700 to 990, b2Overview 170 to 240 |
| owner compliance page | ~900 ms | requireOwnerPageStaff 135 to 260, hub 640 to 825 |

Layout and page render at the same time, so the slower of the two sets the wait. The staff home page is the critical path for staff, and it has more serial steps than the plan assumed: after its Promise.all it still awaits about seven more steps one by one, and the compliance hub loader (`loadHub`) is itself a chain of about four dependent rounds of queries.
