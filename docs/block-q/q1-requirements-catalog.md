# Block Q1 — Onboarding Wizard Requirements Catalog

**Status: requirements/spec document only. No application code, module content, or schema was modified in producing this.**

**Author's role note:** this is the master spec Block Q's actual wizard implementation (Q2 onward) is designed against and graded against. It compiles findings from three independent Block P generalization passes — bar (`docs/block-p/`), pub (`docs/block-p-pub/`), cafe (`docs/block-p-cafe/`) — plus the live Supabase schema as of 7 Sep 2026, into one catalog. Where the three P2 documents genuinely disagree or leave something unresolved, this document says so explicitly rather than picking a side (see "Open items for the orchestrating session" at the very end).

**Locked design decision this catalog respects** (Notion Decision Log, 6 Sep 2026, "Wizard flow design — HYBRID"): structured, guaranteed-entry pages for anything mapping to a required schema/compliance field (Part A below). A build-then-surface-gaps loop applies only to SOP/content-authoring material (Part B below), never to guaranteed compliance fields.

## Part C — Explicitly Out of Scope

**EGM / gaming machine licensing.** Zero schema representation anywhere in the current database, and — separately from the schema gap — a real venue owner explicitly declined to have it included at all: per `docs/block-p-pub/p4-modules/00-module-index.md` item 16, "Gary was explicit that this is handled entirely by an external accountant and compliance provider, and said directly he didn't want a new hire's training relying on his own explanation." `docs/block-p-pub/p2-workflow-schema-pub.md` §1 (node `F1`/`F2`) treats a gaming-entitlement "Yes" as a hard escalate-to-founder branch, not a question the flow attempts to answer. Block Q should preserve this exact behavior: detect the gaming-entitlement question, and if "yes," stop and flag for founder/specialist review rather than building any gaming-specific structured fields or content branches.

**Non-Victoria states/territories.** RSA and food-safety/WWCC regulation is state/territory-specific — different regulator, and WWCC even carries a different name per state (CLAUDE.md, "Compliance content sourcing"). This is a real constraint, not a gap to close: Block Q should design its licensing/compliance taxonomy for Victoria first (matching every P1/P2 document to date, all of which assume Victoria explicitly) and leave the `state` field genuinely open — i.e., a non-Victoria answer must route to a founder-review flag (per Part A's state/territory row), not silently reuse Victoria's licence-type or food-safety-class taxonomy. Do not hardcode "Victoria" anywhere in Q2's implementation; hardcode only the *fallback behavior* for "not yet supported."

## Part D — Grading Rubric

This rubric is written to be handed to a blind-grading agent with **zero knowledge of how the wizard works**. It grades two things independently: whether a Part A field was captured correctly, and whether a Part B topic's authored content clears the bar. Grade each row of Part A and each row of Part B separately; do not average across rows into a single pass/fail for the whole wizard.

### D.1 — How to grade a Part A field

For every field, first check whether its Part A row says **NO CURRENT COLUMN/TABLE** or **NOT YET BUILT**. If so, grade it under D.1.5 below instead of D.1.1–D.1.4 — a field with nowhere to be stored cannot be graded as "present in the database."

**D.1.1 — Generic "present" definition by input type:**
- **text**: non-null, non-empty after trimming whitespace, and **not a placeholder value**. A placeholder value is any of: "TBD", "N/A" (when the field's own condition says it applies), "unknown", "ask [name]", "check with [role]", "-", or any string that is itself a deferral rather than an answer. A field holding a placeholder value does not count as present, even though the database column is technically non-null.
- **select**: non-null and equal to one of the field's documented valid options. A select field is never satisfied by a freetext value smuggled into a text column.
- **number**: non-null, and satisfies the field's stated validation (e.g., positive integer for capacity).
- **date**: non-null, valid calendar date, and satisfies any stated ordering constraint (e.g., `issued_date <= expiry_date`).
- **upload+parse**: the file itself must be present in storage **and** every field the wizard claims to have parsed from it (e.g., an expiry date read off a certificate photo) must independently satisfy its own present-definition above. A stored photo with a null parsed expiry date does not count as present for any feature that depends on the expiry date (e.g., cert-expiry nudges).
- **repeatable-group**: the group as a whole is present only if (a) at least one row exists whenever the field's "Required for" condition evaluates true, and (b) every individual row independently satisfies the present-definition for each of its own sub-fields. One valid row and one placeholder-filled row means the group is only partially present — note this explicitly rather than rounding up to "present."

**D.1.2 — Compliance-critical fields get a stricter bar.** The following fields must trace to a real source document or authoritative confirmation, not spoken recollection, to count as fully present — grade these "present, low-confidence" (not a straight pass) if the only evidence is an interview answer with no document cross-reference, and grade them "fail" outright if two contradictory values were both recorded without resolution: licensed capacity, approved trading hours, licence number/type, ABN, any certificate expiry date, RSA marshal identity, Food Safety Supervisor identity. This directly reflects a real, repeated failure pattern found across all three P4 passes (patron capacity given three ways in the pub interview, occupancy given two ways in the cafe interview, FSS identity unresolved in the pub interview) — a wizard that silently picks one of several contradictory numbers without flagging the contradiction should fail this check even if a value ends up stored.

**D.1.3 — Routing/gating fields** (e.g., "does the venue hold a liquor licence at all," "does capacity trigger crowd control") are graded on whether the correct downstream branch was actually taken, not merely whether an answer was recorded. A "No" answer that still causes the RSA subtree to be asked is a fail regardless of what the stored `select` value says.

**D.1.4 — "Named key role" fields** (RSA marshal, Food Safety Supervisor) additionally require the grader to check: did the wizard flag, in some human-visible way, that this named individual may not yet have a corresponding `app_users` login? A wizard that silently drops this fact after capturing the name (with no visible note that the identity-to-login link is unresolved) should be graded as incomplete on this field even if the name itself is present, because this is a stated, real gap in the current schema design, not a cosmetic nicety.

**D.1.5 — Fields with no schema destination.** A field flagged **NO CURRENT COLUMN/TABLE** or **NOT YET BUILT** should be graded on whether the wizard does one of the following, not on whether a value ends up in a structured column (there is nowhere for it to go):
- **Pass**: the wizard either (a) visibly captures the answer as freetext into a clearly-labeled adjacent field (e.g., a security firm name typed into `venue_contacts.notes` with `contact_type='security_firm'`) with an explicit "not yet a structured field" indicator, or (b) visibly and explicitly tells the user this fact isn't captured yet and why, rather than silently dropping the question.
- **Fail**: the wizard stuffs the value into an unrelated existing structured column (e.g., writing happy-hour hours into `venue_licence_profile.approved_trading_hours`, or a roster-app name into `venues.shift_windows`) — this conflates two different facts under one key, which was explicitly identified and rejected as an anti-pattern in both the bar and pub passes. Also **fail**: silently omitting the question entirely with no visible acknowledgment.

### D.2 — How to grade a Part B topic

**D.2.1 — Minimum structural bar** (a proxy for the Module Content & Assessment Standard; this document could not locate that standard as a standalone file on disk — it is referenced live in Notion by every P2/P4 document but was not found under `docs/`, so the following is a reasonable reconstruction from how all three P4 authoring passes consistently applied it, not a verbatim copy):
- 3–6 sections per module (a topic legitimately needing more should be split into a second module, a validated pattern — e.g., the pub's food-safety content splitting into two modules rather than exceeding the cap).
- 1–2 safety-critical callouts per module, reserved strictly for genuinely safety-critical content (gas/CO2, burns, blade hazards) — not a formatting device for emphasis in general.
- At least one check-question per section, except sections that are purely context-setting (e.g., a pure welcome/orientation section with nothing to comprehension-check).
- Numbered step markers (1/2/3) are reserved for genuine sequences (e.g., the closing procedure) — their presence anywhere else is a content-standard violation per CLAUDE.md's own branding anti-patterns list, not a style preference.
- A restricted (`is_restricted=true`) section must never carry a `check_questions` row.

**D.2.2 — The load-bearing quality check: no fabrication.** For every topic, the grader must check the authored content against the underlying source material (the P3-equivalent seed/interview answers for a real venue) for any confidently-stated fact — a specific number, a specific name, a specific procedure — that does not actually appear in the source. Any such fabrication is an automatic fail for that topic, regardless of how well-formatted the content otherwise is. This is the single most consistently-applied authoring discipline across all three P4 passes (bar, pub, cafe all wrote "ask [name]" or "not confirmed" rather than inventing an answer, dozens of times each) and is more load-bearing than section count.

**D.2.3 — Self-consistency check.** Per CLAUDE.md's own agentic self-testing practice #1: pick every check-question attached to the module and verify it is answerable from that module's own text alone, with no outside knowledge. A check-question that requires information from a different module, or from general knowledge, fails this topic even if the prose itself is accurate.

**D.2.4 — Topic-specific overrides:**
- **Allergen/food-safety topics with a large or modifier-based menu**: sufficient means the content used the principles-based pattern (confirmed facts stated plainly / an honest statement of what isn't recorded / an explicit escalation script such as "I can't confirm that right now") — attempting a full item-by-item matrix in prose is itself a fail on this topic, independent of accuracy, because it violates the section/callout caps by construction once the menu is large or modifier-heavy.
- **Closing procedures**: sufficient requires the content to explicitly reconcile who performs each step against who holds the credential that step needs (the alarm-code-vs-who-sets-it gap found in the bar pass) — a closing sequence that assigns a task to a role without confirming that role can actually complete it is a fail.
- **Trading hours / licence / capacity module**: sufficient requires every number stated to trace to (or explicitly defer to) the corresponding Part A structured field — this topic fails if it asserts a number that contradicts, or was never cross-checked against, `venue_licence_profile`.
- **Restricted-tier modules**: sufficient requires (a) `is_restricted=true` set correctly on both `knowledge_chunks` and `module_sections`, (b) `module_roles` scoping limited to roles the venue actually named as authorized, (c) no attached `check_questions`, and (d) no placeholder/fictional value left in place of a real one without an explicit, visible flag that it's a placeholder (the bar, pub, and cafe passes all used clearly-marked fictional codes for testing — a real venue's content must never ship with an unflagged placeholder).

**D.2.5 — Ask Larder test-set cross-check.** Where a Part B topic overlaps with the standing four-question Ask Larder test set (in-scope / fallback / out-of-scope / adversarial, per CLAUDE.md's Build Manual Part C), the grader should additionally confirm at least one real question from that topic was run through the test set and produced the expected category of answer, using the P5 transcripts referenced in each Part B row as the calibration example of what "correct" looks like for that topic.
